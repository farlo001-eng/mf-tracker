## Current State (2026-07-07)

Owner tracking (individual/company + owner-to-owner links) and a reworked Desk tab
(Follow-ups + Hotlist) are in. Owners remain distinct from the free-text `owner_name`
field on properties (imported data stays sacred/untouched); `owner_id` is the link layer.

### Fixed same day: Desk Hotlist/Follow-ups showed address instead of property name
`GET /api/desk`'s property query hardcoded `p.address as name`. There is no
`property_name` column — the property's display name lives in the `extra` jsonb field
under the key `"Property Name"` (same field the property detail modal title falls back
on, `App.jsx:615`: `detail?.extra?.["Property Name"] || detail?.address`). Fixed the
query (`server.js`, `/api/desk` property branch) to
`coalesce(nullif(p.extra->>'Property Name', ''), p.address) as name` so blank/null names
fall back to address. Follow-ups and Hotlist both read from the same `rows` array this
query builds, so the fix covers both sections with one change. Owner rows (`o.name`)
were already correct and untouched.
**Note for later**: the main Properties table itself does NOT apply this fallback in its
own "Property Name" column (`colVal` in `App.jsx` returns `p.extra?.["Property Name"] ??
""` with no `|| address`) — only the detail-modal title does. If the fallback should also
show in the Properties table's own column, that's a separate, not-yet-requested change.

### Fixed same day: Desk showed 0 items in both sections
Root cause: `GET /api/desk` was registered in server.js *after* the Express catch-all
(`app.use(express.static(dist)); app.get("*", ...)` that serves `index.html` for the SPA).
Express matches routes in registration order, so every request to `/api/desk` matched the
catch-all first and got back `index.html` with a 200 status. The frontend's `api.get`
helper (`fetch(u).then(r => r.ok ? r.json() : Promise.reject(r))`) saw `r.ok === true` and
tried to `.json()`-parse HTML, which threw — and `DeskView`'s `load()` swallowed that
rejection with a bare `.catch(() => {})`, so the UI silently rendered the "nothing due" /
"nothing on desk" empty states instead of surfacing a failure. The SQL/filter logic itself
was correct the whole time.
Fix: moved the `/api/desk` route (and its `pad2`/`todayStr`/`addDaysStr` helpers) to
before the "serve built client" block. Also added a `loadError` state to `DeskView` — a
failed `/api/desk` fetch now shows a red-bordered error card instead of a false empty
state, so this class of bug is visible next time instead of silent.
**Lesson**: any new API route added to server.js must go above the
`app.use(express.static(dist))` / `app.get("*", ...)` catch-all, or it will silently
404-via-index.html instead of ever reaching its handler.

### DB additions (db.js)
- `owners` table + `owners.type` (`'individual'|'company'`, default `'individual'`,
  app-layer validated only — no db enum).
- `properties.owner_id` — nullable FK to owners, `on delete set null`.
- `touches.owner_id` — nullable FK to owners, cascade; `touches.property_id` nullable;
  `touches_one_target` CHECK enforces exactly one of property_id/owner_id (guarded via
  `do $$ ... exception when duplicate_object ... end $$` so re-running ensureSchema on
  every boot doesn't error the 2nd+ time).
- `owner_links` table (owner_id_a, owner_id_b) — many-to-many owner-to-owner links, with
  a unique index on `(least(a,b), greatest(a,b))` so link direction doesn't matter.
- `schema_flags` table — generic one-row-per-key marker table for guarding one-time
  migrations (first user: `owner_type_guess_v1`). Prefer this pattern over ad-hoc
  "is the table still empty" checks for any *future* one-time migration, since it doesn't
  get confused by a user's later manual edit that happens to match the "untouched" state.
- Guarded migrations run inside `ensureSchema()`:
  - `migrateOwnersFromPropertyNames()` — backfills owners from properties.owner_name
    (guarded by `owners` table being empty).
  - `guessOwnerTypesFromNames()` — regex keyword match (LLC/INC/CO/GROUP/TRUST/etc,
    word-bounded, case-insensitive) sets `type='company'`; guarded by `schema_flags`.

### Server additions (server.js)
- Owners: `type` added to POST/PATCH (validated to individual|company, 400 if not);
  `GET /api/owners` list + `?q=` search both accept `type=` and `active=true|false`;
  `GET /api/owners/:id` now also returns `linkedOwners: [{id,name,type}]` (joined through
  `owner_links` both directions); `POST /api/owners/:id/links` `{linkedOwnerId}` and
  `DELETE /api/owners/:id/links/:linkedOwnerId`.
- `GET /api/properties` — `active` param now also accepts `true`/`false` (was `1`-only).
- New `GET /api/desk?type=&status=&market_id=` — returns `{ followups, hotlist }`.
  `followups` = active owners+properties that HAVE a next_follow_up, each tagged with a
  `bucket` (`overdue|today|upcoming|later`, computed from server-local today ± 7d) and
  sorted bucket-then-date. `hotlist` = ALL active owners+properties, flat, unbucketed.
  `market_id` only filters the properties half (owners have no market). Channel filtering
  is intentionally NOT a server param — the frontend filters `last_channel` client-side.

### Client additions (App.jsx)
- **Desk tab rebuilt**: shared filter bar (All/Properties/Owners segmented type toggle,
  status dropdown, market dropdown [disabled when Owners-only], channel dropdown, search)
  feeds one `GET /api/desk` call. Two visually distinct `.card` sections below it:
  - **Follow-ups** — bucketed (`DESK_BUCKETS`), `DeskFollowupRow` per item: name/status/
    last-touch, channel icon, overdue/due-today/date pill, +3d/+1w/+2w/+1mo quick buttons,
    a "log touch" icon button (opens the property/owner modal — no inline touch UI here),
    and a star to unstar (PATCH active:false) without leaving the page.
  - **Hotlist** — flat sortable table (`DeskHotlistRow`, click-header sort like
    OwnersView), same unstar action, next_follow_up shown as a plain column (no bucket
    framing, "—" if unset).
  - `DeskTypeBadge` is the shared Owner/Property pill used in both sections.
- **"On desk" filter replaces the old Desk/Warehouse toggle** in both `PropertiesView`
  (server-side, `active=true` query param) and `OwnersView` (client-side, since that view
  already filters everything client-side) — a pill next to the status pills, matching
  that visual language instead of a segmented tab.
- **Owner type**: `OwnerTypeToggle` (Individual/Company segmented control) used in both
  `AddOwnerForm` and `OwnerModal` (patches `type` directly on change in the modal).
- **`OwnerLinksSection`** in `OwnerModal`, below Linked Properties — shows a "People"
  section if the current owner is a company, or "Companies" if individual. Search box
  hits `/api/owners?q=&type=<opposite>`; click a result to link, "+ Create new
  <opposite type>" to create-then-link, "Unlink" per row. Clicking a linked owner's name
  calls `onOpenOwner` (now threaded from `Tracker` into `OwnerModal` alongside
  `onOpenProperty`) to swap the currently-open overlay to that owner.
- No new CSS was needed anywhere in this pass either — reused `.pill`, `.link`, `.card`,
  `.tbl*`, `.colpop`, `.row-btn`, the existing segmented-toggle inline-style pattern, etc.
