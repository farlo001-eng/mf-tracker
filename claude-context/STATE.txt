## Current State (2026-07-06)

Owner tracking added. Owners are now first-class records, distinct from the free-text
`owner_name` field that stays on properties (imported data remains sacred/untouched).
Properties link to owners via a nullable `owner_id` FK.

### DB additions (db.js)
- `owners` table: id, name, status, active, phone, email, mailing_address,
  next_follow_up, notes, created_at
- `properties.owner_id` — nullable FK to owners, `on delete set null`
- `touches.owner_id` — nullable FK to owners, `on delete cascade`; `touches.property_id`
  is now nullable too. `touches_one_target` CHECK constraint enforces exactly one of
  property_id / owner_id is set per touch row (added via a guarded `do $$ ... $$` block
  so re-running ensureSchema on every boot doesn't error on the second run).
- `idx_props_owner`, `idx_owners_active`, `idx_touches_owner` indexes
- One-time backfill `migrateOwnersFromPropertyNames()` runs inside `ensureSchema()`,
  guarded to only fire while the `owners` table is still empty: creates one owner per
  distinct (case-insensitive, trimmed) `owner_name` across existing properties (first-seen
  casing wins), links matching properties, logs counts created/linked.

### Server additions (server.js)
- Full owners CRUD: `GET/POST /api/owners` (list has property_count/total_units/last_touch/
  last_channel rollups; `?q=` does a lightweight ilike name search for the combobox),
  `GET/PATCH/DELETE /api/owners/:id` (detail includes linked `properties[]` and `touches[]`),
  `POST /api/owners/:id/touch`, `POST /api/owners/merge` (`{survivorId, loserIds}` —
  repoints properties/touches then deletes losers, transactional).
- `PATCH /api/properties/:id` allows `owner_id` now.
- `GET /api/properties` and `GET /api/properties/:id` both join `owners` and return
  `linked_owner_name` (list) / `linked_owner_name` + `market_name` (detail).
- `POST /api/import` links/creates an owner per row from `owner_name` (case-insensitive
  match, per-request in-memory cache to avoid duplicate lookups within one import),
  returns `ownersCreated` alongside `imported`.

### Client additions (App.jsx)
- Top-level nav: **Desk / Properties / Owners** tabs, owned by `Tracker`. `Tracker` also
  owns `expandedPropertyId` / `expandedOwnerId` (so any view can open either overlay) and
  a `refreshKey`/`bump()` pair so mutations in one view refresh data in the others.
- `DeskView` — unified due/overdue list merging active owners + active properties
  (client-side merge + sort by next_follow_up), badge per row ("Owner"/"Property"),
  channel icon, click opens the right overlay.
- `PropertiesView` — the old Tracker body (market filter, Desk/Warehouse sub-tab, search,
  columns picker, filters, status pills, table). `PropertyRow` no longer owns modal state;
  it just renders the row and calls `onOpen()`. New `owner_id` column (type `"owner"`,
  in `CORE_COLS`/`DEFAULT_COLS`) renders a clickable owner chip or a muted "+ link"
  affordance, both open the property modal.
- `PropertyModal` — extracted from the old inline PropertyRow modal so it can be opened
  from anywhere (Desk, Owners, or the table) by id alone; fetches its own detail. New
  "Linked owner" section renders `OwnerLink`.
- `OwnerLink` — combobox: searches `/api/owners?q=`, links on click; if no owner_id and
  `owner_name` is non-blank, offers "+ Create new owner named '...'" (editable) which
  POSTs then links; shows chip + "Unlink" once linked.
- `OwnersView` / `OwnerRow` / `AddOwnerForm` — sortable table (click header toggles
  asc/desc) mirroring the properties table's visual language; Desk star toggles `active`.
- `OwnerModal` — same structural/CSS pattern as PropertyModal: editable fields, touch
  logger + history (reuses `TouchRow` as-is — it already just hits `/api/touches/:id`),
  linked-properties list (click opens `PropertyModal` for that property), delete.
- No new CSS was needed — everything reuses `.link`, `.pill`, `.card`, `.tbl*`, `.colpop`,
  `.row-btn` etc.

### Known gap / manual step required
No `pg_dump`/Railway CLI/`DATABASE_URL` were available in the dev sandbox that built this,
so the pre-migration production backup (task step 0) was **not** run automatically.
Before deploying, run:
`pg_dump $DATABASE_URL > backup_pre_owners_$(date +%Y%m%d).sql` and confirm the file is
non-empty. The owners backfill migration runs automatically on next boot via
`ensureSchema()` — it is additive/guarded, but the backup should still happen first.
